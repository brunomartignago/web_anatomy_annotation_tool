# Architecture (target)

A **local web app**. A Python backend owns capture, data, rules and suggestions. A browser frontend owns the annotation experience. Everything runs on the annotator's machine. Nothing is uploaded anywhere.

```
┌────────────── capture ──────────────┐      ┌──────────── annotate ────────────┐      ┌──── research ────┐
 urls.csv ─▶ Playwright ─▶ page.png         Browser UI (React + canvas)               exporters
                        ├▶ dom.json  ─┐       ▲  draw · select · accept · fix          ├ research CSV
                        └▶ meta.json  │       │  REST (FastAPI)                         ├ YOLO / COCO
                                      ▼       ▼                                         ├ summarized templates
                              suggesters ─▶ annotations.json  ◀──────────────────────── └ archetype stacks
                              (dom · rule · prior · model*)
```

## Project data on disk (git-ignored)

```
data/projects/<project>/
├─ project.yaml                   name, taxonomy id, url list, created_at
└─ pages/<page_id>/
   ├─ page.png                    full-page screenshot (Playwright full_page=True)
   ├─ meta.json                   url, title, viewport, size, locale, captured_at, blocked?
   ├─ dom.json                    visible elements: bbox, tag, role, attrs, text length, styles, parent index
   ├─ annotations.json            schema v1
   └─ .cache/strips/*.webp        generated by the server
```

These are plain files, so a project can be zipped, shared or diffed. There's no database until it's needed.

## Key decisions and why

| Decision | Why |
|---|---|
| **Local web app** instead of tkinter | Tiled rendering handles 91,000-px pages. A web UI gives a better interaction ceiling, attracts designer and front-end contributors, and allows a GitHub Pages demo. |
| **Python backend** | Capture (Playwright), geometry, rules, and later ML all live in Python, and the legacy code is Python. |
| **Taxonomy in YAML, not in code** | Contributors can propose classes without touching code. Other researchers can plug in their own taxonomy (which also delivers the "customizations" goal). |
| **JSON Schema as the contract** | Generates both pydantic validation and TS types, so the frontend and backend can't drift apart. |
| **Top-left pixel `[x,y,w,h]`** | This matches the browser, Playwright and COCO. Exporters convert to the bottom-left convention used in the research. |
| **Suggestions are data, not truth** | Every box and label records `source`, `confidence` and `status`. This answers the theory's critique of crawlers: the DOM proposes and the human decides. It also lets you measure suggestion accuracy. |
| **Vertical strips, not a deep-zoom pyramid** | Pages are 1920 px wide and very tall. 2048-px strips are simple, cacheable and enough. Move to OpenSeadragon only if needed. |
| **No database** | One JSON file per page with atomic writes. Git-friendly and easy to back up. Revisit if multi-user is needed. |

## The suggestion pipeline

```python
class Suggester(Protocol):
    id: str                       # "dom" | "rule" | "prior" | "model" | "llm"
    def suggest(self, page: Page, annotations: list[Annotation]) -> list[Proposal]: ...
```

- A `Proposal` either adds a box (bbox + labels + confidence) or labels an existing box.
- Suggesters run in a fixed order (**dom → rule → prior**) and are merged by `suggest/base.py`.
- Merge rules: a **human label is never overwritten**; otherwise higher confidence wins, and ties go to the later suggester.
- New suggesters (a trained model, an optional vision LLM) are drop-in modules registered in `cli.py`. This is the main extension point for contributors.

### DOM suggester (Phase 4, depends on Phase 1 capture)
`dom_extract.js` walks the rendered page and keeps elements that are visible, non-zero in size, not fully covered, and either leaf-like (text, media, form controls) or semantic containers (`nav`, `header`, `footer`, `article`, `table`, `[role]`). It records document-space boxes, so they line up exactly with `page.png` because both come from the same Playwright session. Fixed and sticky elements are flagged as Overlay candidates.

### Rule suggester: the theory as code
1. Find section candidates: `header` and `footer` landmarks, full-width bands, and large containers.
2. Cluster the boxes inside each band into columns by horizontal gaps. Number them left to right, using 0 for a single column.
3. A first or last column narrower than 20% of page width is a Panel. A Panel whose elements are at least 50% links is a Menu.
4. Elements inherit `Taxonomy` from the section that contains them.

### Prior suggester
Counts Form·Function·Component co-occurrence across accepted boxes. It re-ranks the 1–9 presets per project and fills in the attributes left over after the DOM pass. For example, if Function is Heading, Form is Typo with p≈0.99.

## Interaction model (how "fewer clicks" happens)

| Today (v2) | Target |
|---|---|
| Draw each box by hand | Boxes arrive pre-drawn from the DOM. Draw only what's missing. |
| 4 picks per box | **Review mode**: Enter accepts the suggestion. Use 1–9 for a whole preset, or `f`/`n`/`c`/`t` then a letter to fix one attribute. |
| Taxonomy picked on every element | Draw or confirm about 5 section boxes per page, and every element inside inherits its section. |
| Component picked on every element | Inherited from the parent component box (a link inside a Menu box gets Menu). |
| Repeated cards and list items labeled one by one | **Select similar** (same DOM signature or size/row), then one keystroke labels them all. |
| Only options 1–9 reachable | Every option has a mnemonic. `/` opens a type-to-filter command palette. |
| One image via file dialog | Page queue with progress. `]`/`[` move to the next/previous page. Always autosaves. |

**Success metric:** actions per accepted box, logged in `history.actions`. v2 needs at least 5 per box (draw plus 4 picks). The target is ≤1.5 on DOM-friendly pages.
